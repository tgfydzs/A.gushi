## 表1 · 设计点（原则层）→ 落点

| # | 设计点 | 含义 | 落在哪些层/模块 | 具体实现方式 |
|---|--------|------|----------------|-------------|
| P1 | **Python负责** | 状态维护、调度、数据结构、Prompt管理、JSON解析都不给LLM | 全部规则模块 + 全部支撑模块 | N0/N1/N7/N8/心跳调度/GameController 纯代码 |
| P2 | **LLM负责** | 只做需要智能的部分 | N2/N3/N45/N6/N6-Player/N9a/N9b/N9c | 8个调用点 |
| P3 | **LLM无状态** | LLMClient 不存任何上下文，调用方全权管理 | `LLMclient.py` | 每次调用由调用方传入完整 messages 列表 |
| P4 | **LLM输出必须JSON** | 所有层输出结构化，代码可校验 | 8个LLM调用点 | `safe_json_loads()` 统一解析（4级降级） |
| P5 | **信息隔离** | 每层只给最小上下文 | N2/N3 不给玩家实例；N45 不给玩家实例；N9 只给摘要 | 见 表3 数据流 |
| P6 | **N6唯一接受玩家实例** | 防止玩家隐藏信息泄漏进NPC对白 | N6 接受全量玩家实例；N6-Player 接受玩家实例；**N2/N3/N45 均不接受** | N2/N3 只拿玩家的 名称/位置/实力；N45 完全不拿 |
| P7 | **增量输出** | 只传变化，不传全量 | N45 / N6 / N6-Player / N9c | `{"增加":{...},"删减":{...}}` + `apply_npc_delta`/`apply_player_delta`/`merge_delta` |
| P8 | **可撤回** | 每轮执行前全量快照，`!!` 回滚 | GameController.snapshot/restore + N9_director.to_dict/restore | 深拷贝 9 类状态；回滚时清空 DeferredQueue |
| P9 | **数据驱动** | 数值/名称/行为参数从世界配置读 | `B1WorldLayer.get_config()` | 9个配置项，见 表2.4 |
| P10 | **三种上下文分离** | 全局/事件/导演，可见性和生命周期不同 | GameController + ContextHistory | 见 表3 上下文 |
| P11 | **温度分层** | 严谨判定用低温、创意写作用高温 | N9a=0.3 / N9b=0.9 / N9c=0.6 | 仅 N9 显式设温度；**N2/N3/N45/N6 用API默认** |
| P12 | **后台化不阻塞** | 世界演进不占玩家等待时间 | HeartbeatManager + DeferredQueue | 心跳起独立线程；N0 下一轮消费 |
| P13 | **后台不共享实例** | 线程安全 | DeferredQueue | 只传序列化增量，不传 NPC 对象引用 |
| P14 | **Prompt客制化** | prompt 与世界观解耦 | `load_prompt()` + `data/prompt/{层}_custom/*.md` | 7个文件有映射；`{中文占位符}` 替换 |
| P15 | **防幻觉** | 过滤LLM编造的名称 | ⚠️ **部分已失效** | 见 表5 问题清单 |
| P16 | **合并层级按信息集判定** | 两层能合 ⟺ 输入信息集相同 | 本轮新增的设计约束 | 见 表5 边界 |
| P17 | **分层模型路由** | 不同层可用不同模型 | `base_cnf.LAYER_MODEL_OVERRIDE` + `LLMClient(layer)` | ⚠️ 表为空，当前所有层同模型 |
| P18 | **连接池复用** | 省 TCP+TLS 握手 | `LLMClient.__init__` 的 `requests.Session` | 实例级，N45/N6 的并行线程共享 |

## 表5 · 盘点中发现的问题（供重构决策）

### 5.1 文档与代码不符（CLAUDE.md 已过时）

| 文档声称 | 实际情况 |
|---------|---------|
| 「使用 `resolve_npc_name()` 进行3级名称匹配」 | ❌ **该函数不存在**。实际是 `B3NPCListLayer.get_npc()`：去括号前缀 + `in` 子串匹配，未命中返回 None |

| 「N4/N5 层」 | 已合并为 N45（本轮） |

### 5.2 死代码 / 未消费

| 项 | 状态 |
|----|------|
| `move_to` 字段 | N2 输出，主循环从未读取 |
| `GameClock.is_night()` / `is_daytime()` | 定义完整，**全代码无调用** |
| `表更新成本UpdateCost` | 存在于 NPC 表和 prompt 输入格式，**无代码读取或使用** |
| `NPC_关联距离_段` 配置项 | 代码中无读取点 |
| `common/N4_reasoning.py` · `common/N5_response.py` · `prompt/N8_time_ability_sys.txt` | 本轮弃用，无引用 |

### 5.3 潜在风险

| 项 | 说明 |
|----|------|
| **NPC表截断不完整** | `cap_fields()` 只截 observation(20) / memory(30) / pending(11)。**对玩家观察PlayerObservation、好感度Relationship、信念Belief、生活目标Goals 无上限**，长期运行会无限增长，且每轮随 `to_dict()` 全量喂给 N45/N6/N9c |
| **`new_context()` 不重置 count** | 事件轮次号跨事件持续累加，N2 prompt 里的"轮次号"会越来越大 |
| **N2/N3/N45/N6 温度未设置** | 只有 N9 显式设温度，其余用 API 默认。N45 生成对白 vs N6 客观收尾，可能需要不同温度 |
| **分层模型路由未启用** | `LAYER_MODEL_OVERRIDE` 为空 |
| **N6 是延迟瓶颈** | 实测 18.3s / 整轮 33.7s（55%）。输入是11张全表，输出最多6张表的增量 |

### 5.4 信息集边界（合并层级的硬约束）

| 边界 | 为什么不能跨 |
|------|-------------|
| N2/N3 ↔ N45/N6 | 前者不碰 NPC 表，后者不碰全局 NPC 名单。合了每轮要把全量 NPC 档案塞进每个 NPC 调用 |
| **N45 ↔ N6** | N6 持有玩家实例，N45 必须不持有。合了 = 把玩家隐藏信息交给生成对白的层（破 P6） |
| N9a ↔ N9b | 温度需求相反（0.3 严谨 vs 0.9 创意） |
