# 通用 AI 叙事框架设计(暂名 `verve`)

> 依据 gushi3 的设计抽象而来。层级清晰是硬约束,为此可做妥协。
> 本文档是后续开发的蓝图,不是最终实现。

---

## 一、核心命题

**框架 = 一套纯连接骨架。它只认识「层和层的连接」+「每层收什么、出什么」。框架不认任何世界规则——它不把任何东西标记为"规则",只把玩法包素材原样传给 LLM。世界怎么长、怎么运作,全是玩家给的。**

一句话:**框架连"世界规则"这个概念都不认识,它只认识层的连接。**

（修正说明:此前「框架不认识修仙」的说法仍隐含框架认识"世界规则"这一概念,是错的。二者有本质区别——框架一旦有"规则"概念,就会把规则文件当权威"依据"喂给 LLM,LLM 就照章办事,失去提炼和选择性忽视的能力。）

---

## 二、三层结构

```
┌─────────────────────────────────────────────────┐
│  玩法包 (Pack) —— 玩家提供的一切                  │
│  ── 定义:这个世界的"层模板 + 世界规则 + 实体"     │
└──────────────────────────┬──────────────────────┘
                           ▼
┌─────────────────────────────────────────────────┐
│  框架内核 (Execution Kernel) —— 题材无关          │
│  ── 加载玩法包 → 校验 → 调度层 → 应用 delta       │
│  ── 不认识"金丹期",只认识"第3阶晋升第4阶"         │
└──────────────────────────┬──────────────────────┘
                           ▼
┌─────────────────────────────────────────────────┐
│  LLM 接入点 —— 按玩法包规则执行                   │
│  ── 注入玩家规则 → 调 LLM → 解析输出              │
└──────────────────────────┬──────────────────────┘
                           ▼
┌─────────────────────────────────────────────────┐
│  Godot 交互壳 —— 加载玩法包/显示/玩家输入/叙事    │
└─────────────────────────────────────────────────┘
```

## 三、玩法包(Pack)结构

玩家提供的一切,格式化为一份完整定义。**它是"玩家作者身份"的载体。**

```
玩法包/
├── manifest.json      玩法包元数据:名称/描述/启用哪些层
├── layers/            每个 LLM 层的模板 + 注入点
│   ├── update.json        {输入: 结论+两实体实例, 输出: npc增量/玩家增量/旁白, 注入: 规则文件}
│   ├── reason.json        {输入: 实体+感知, 输出: 增量}
│   ├── perceive.json      {输入: 实体列表+事件, 输出: 各实体感知+传播}
│   └── ...(由 gushi3 的 N2-N9 抽象而来)
├── world/             世界素材(这个世界是怎样的,不是"你必须怎么做")
│   ├── 修炼体系.md         (这个世界的力量体系是怎样的)
│   ├── 战斗.md             (这个世界打起来是怎样的)
│   ├── 势力.md             (这个世界势力间是怎样的)
│   └── ...
├── entities/          玩家定义的世界实体
│   ├── npc_template.json    (NPC 模板)
│   ├── location_tree.json   (地点树)
│   └── ...
```

**关键:玩法包不是"预置世界",是"玩家作者的作品"。** 修仙只是玩家喂进去的其中一个玩法包。

**玩法包提供的是"素材",不是"执行指令"。** 框架不把它们分类为"规则 / 数据 / 实体"——那是玩法包自己的组织方式。素材是"世界是怎样的"(如"此方天地灵气稀薄,筑基已是万中无一"),而非"你必须这么做"(如"突破必须消耗灵石500")。

**但素材 ≠ 全量知识。** 完整记住然后合理总结忽略,才是 AI 数据处理的正确方式。过于复杂的知识,会影响 AI 的判断,对理解造成污染,乃至污染产出。因此:
- **记型而不记意**:保留世界的形态/结构(谁是谁、势力什么立场、事件框架),不保留具体意图/具体措辞/具体过程。形可记,意会随时过时、会误导。
- **记逻辑框架**:记录"这类事情在这个世界是怎么发生的"(晋升的逻辑、冲突的逻辑、传播的逻辑),是可复用的结构,不是一次性细节。
- **按需要带入内容**:到了特定时刻,才把与该时刻相关的具体内容注入 LLM 上下文——其余的全部不喂。

一句话:**框架记忆的是"可复用的逻辑结构 + 实体的身份形态",到了需要的时刻才把相关内容带进去;无关的一切不进上下文。**

## 四、层契约(从 gushi3 抽象)

每层只定义 **输入 → 输出**,内部判定由玩法包注入。

| 层 | 输入契约 | 输出契约 | 玩法包素材(LLM 参考,非硬规则) |
|----|---------|---------|-----------------|
| 感知层 | 实体列表 + 当前事件 | 各实体感知内容 + 传播信息 | 这个世界信息如何流动的素材 |
| 推理层 | 实体实例 + 感知 | 实体增量 | 这个世界实体如何理解事物的素材 |
| 回应层 | 实体实例 + 感知 + 上下文 | 回应文本 + 内心想法 | 这个世界实体会如何说话的素材 |
| 更新层 | 结论 + 两个实体实例 | npc增量 + 玩家增量 + 旁白 | 这个世界对结论如何响应的素材 |
| 导演层 | 世界状态 + 时间 + 事件 | 世界事件 + NPC幕后行为 + 传播 | 这个世界暗线如何推进的素材 |
| ... | (其他层由 gushi3 N2-N9 抽象) | | |

**玩法包素材 = 玩家提供的内容,不是规则。** gushi3 里 `{攻击行为旁白参考}` 这种占位符注入机制,扩展为注入整个世界的素材。但注入的是"世界是怎样的",不是"你必须怎么做"。LLM 拿到素材后自己提炼、判断、选择性运用——框架不把任何注入内容打上"规则"标签。

---

## 五、LLM 自由度(验证点,不预设)

自由度由**玩家素材的粒度**天然决定:

- 素材写"突破金丹需灵石500" → LLM 被自然约束
- 素材写"突破需稀缺之物" → LLM 自由决定具体是什么
- 素材是"世界是怎样的"而非"你必须怎么做" → LLM 必须提炼和选择,而非照章办事
- **素材细 → 稳定;素材粗 → 多元**

验证点:哪种素材粒度组合在 gushi3 的 N9 下效果最好。这是后续需要实测验证的,不是现在拍板的。

## 六、AI 依赖问题(本设计的动机)

**AI 过分依赖依据,而不是提炼和选择性忽视。** 这是本设计要解决的核心问题之一。

当框架把规则文件当作权威"依据"喂给 LLM,LLM 会照章办事——机械执行,不做判断,失去"提炼"和"选择性忽视"的能力。其根源是框架预设了"规则"这个概念。

本设计从源头避免:
1. **框架不认"规则"这个概念** → 没有东西会被框架打上"权威依据"的标签
2. **玩法包只提供"素材"**(世界是怎样的)→ LLM 面对素材,必须自己提炼世界运作方式
3. **LLM 判断轻重、选择性运用素材** → 不被任何"依据"束缚

框架的职责是「调度 + 传数据 + 存状态」,永远不说"这是规则,你要遵守"。

---

## 七、设计原则(硬约束)

1. **层级清晰第一** —— 每层职责单一、接口明确,为后续改动迭代做准备。宁可做妥协(如合并一些层),也要保持边界清晰。
2. **玩法包即契约** —— 玩家数据是框架和 LLM 之间唯一的契约。框架不预设任何题材,也不预设"规则"这个概念。
3. **框架只认结构,不认语义** —— 框架认识层的连接、数据流、状态容器;不认识什么算规则、什么算实体类型。
4. **LLM 是理解者,不是照章办事者** —— LLM 面对玩法包素材,自己提炼世界运作方式、判断轻重、选择性运用。
5. **delta 增量输出** —— 层输出增量而非全量,与 gushi3 一致。
6. **代码层防幻觉** —— 所有 LLM 返回的实体名、位置名经校验。这是 gushi3 已验证的正确架构,保留。

## 八、第 1 版范围(里程碑)

1. **契约文档**:把 gushi3 的 N2-N9 抽象成题材无关的层契约(输入/输出/素材)
2. **玩法包格式规范**:层素材 + 世界素材 + 实体模板的格式
3. **记忆分层设计**:身份/形态(长期稳定)、逻辑框架(长期复用)、当前事件细节(短期用完即弃)三层。明确每层怎么存、何时带进上下文、何时丢弃
4. **Godot 骨架**:加载玩法包、世界模型、层调度(LLM 桩)、玩家输入循环、叙事显示
5. **用现有仙侠数据做一个玩法包**,验证框架能跑通(作为验证样本,不是预设)

记忆分层是第 2 版的骨架:**玩法包提供逻辑框架 + 实体形态(记型不记意),当前事件细节用完即弃(不污染长期记忆),每轮只把相关的逻辑框架带进 LLM 上下文(按需要带入内容)。**

## 九、与现有项目重合度

| 项目 | 重合点 | 差异 |
|------|--------|------|
| Inworld AI / Convai | NPC 由 AI 驱动,行为可配置 | 它们卖 NPC 给游戏,你是玩家自定义整个世界玩法 |
| AI 角色扮演游戏 | AI 自由生成剧情 | 它们 AI 主导,你是玩家规则主导 |
| Tabletop RPG / Dwarf Fortress | 复杂系统模拟 | 它们系统代码写死,你是玩家数据驱动 + LLM 软性 |
| Cairn / LLM 叙事研究 | LLM 生成世界、玩家编辑 | 它们偏学术,你偏工程落地 |

**核心差异化:玩家是规则的作者,AI 是规则的执行者。** 需要验证的甜区是"玩家规则硬 vs LLM 自由"的平衡点。
