# gushi2 项目总结

> AI 多NPC世界模拟框架 — 玩家输入自然语言，系统通过 LLM 驱动流水线逐层处理，生成连贯叙事输出。

---

## 一、项目定位

一个**文字冒险/叙事生成引擎**。玩家扮演一个角色进入幻想世界（默认"苍月大陆"），输入自然语言描述行动，系统背后有多个 NPC，每个 NPC 有自己的性格、知识、信念、记忆、关系和目标。系统通过 **6 层 LLM 流水线** 逐层处理玩家输入，最终输出一段连贯的叙事文字。

**核心体验**：玩家说一句话 → 系统告诉你这个世界发生了什么、NPC 们如何反应。

---

## 二、整体架构

```
用户输入 → main.py (入口+CLI)
              ↓
         WorldEngine (主调度器，驱动 Tick)
              ↓
    ┌─────────┼─────────┐
    ↓         ↓         ↓
  Node层   Context层  Engine层
 (6个LLM节点) (数据容器) (存储/写入/日志)
```

### 三层结构

| 层 | 目录 | 职责 |
|----|------|------|
| **Schema** | `Schema/` | 数据定义 — 所有实体（NPC、世界、事件、记忆等）和暂态容器的数据结构 |
| **Engine** | `engine/` | 引擎 — 调度、存储、写入、LLM管理、加载、持久化 |
| **Nodes** | `nodes/` | LLM 节点 — 每个节点负责一个处理环节，调用 LLM 完成特定判断 |

---

## 三、Tick 流水线（核心流程）

每个 Tick（一轮处理）按**固定顺序**执行 6 个步骤：

```
玩家输入 
  → N7 事件层    : 判断是延续当前事件还是新事件
  → N11 感知层   : 每个 NPC 感知到了什么（信息闸门）
  → N15 推理层   : NPC 对 pending（待解释事件）进行推理
  → N16 回应层   : NPC 生成具体回应（说话/行动）
  → N17 导演层   : 整合所有回应为一段连贯叙事
  → N18 传播层   : 信息在 NPC 之间传播（口口相传/谣言）
  
  每层结果通过 N12 UpdateEngine 写入持久数据
```

| 节点 | 编号 | 调用 LLM? | 做什么 |
|------|------|-----------|--------|
| EventNode | N7 | 是 | 判断玩家输入是延续当前对话还是新事件，确定地点、话题、参与者 |
| PerceptionNode | N11 | 是 | 每个 NPC 感知到的内容（可能漏掉/误解），写入 observation 和 pending |
| ReasoningNode | N15 | 是（有前置检查） | NPC 对有 pending 的事件推理，产生新知识/信念/目标/情绪变化 |
| ResponseNode | N16 | 是 | NPC 生成具体回应（说话、行动），以及好感度变化 |
| DirectorNode | N17 | 是 | 整合所有 NPC 回应为一段文学性叙事输出 |
| PropagationNode | N18 | 否（程序逻辑） | 信息在 NPC 间传播，按 hop 数控制失真度 |
| UpdateEngine | N12 | 否 | **唯一数据写入口**，所有节点输出通过它写入 Entity |

## 四、各目录/文件职责

### 4.1 入口文件

| 文件 | 职责 |
|------|------|
| `main.py` | 程序入口。参数解析、引擎创建、CLI 交互循环（支持交互/单次/debug 模式） |
| `diagnose.py` | 诊断脚本。验证 N7→N18 完整数据流正确性 |
| `requirements.txt` | 依赖（仅 pytest） |

### 4.2 engine/ — 引擎层（13 个文件）

| 文件 | 职责 |
|------|------|
| `world_engine.py` | **主调度器**。驱动 Tick 流水线，按顺序调用 6 个 Node，管理场景记忆 |
| `context.py` | **WorldContext**。运行时上下文容器，单 Tick 存活，持有所有 Node 可读的状态引用 |
| `memory_store.py` | **MemoryStore**。持久数据存储，持有 NPC/WorldState/CurrentEvent 等 |
| `update_engine.py` | **N12 UpdateEngine**。唯一数据写入口，校验后写入 Entity。每层有独立 apply_xxx 方法 |
| `llm_manager.py` | **LLMManager**。LLM 调用管理层。Node 只能通过它调用 LLM。含 MockLLMManager |
| `llm_client.py` | **LLMClient**。LLM 调用抽象基类 + MockLLMClient（测试用） |
| `prompt_loader.py` | **PromptLoader**。加载 `prompts/*.md` 模板并填充变量，内置缓存 |
| `loader.py` | **WorldLoader**。从 `data/` 加载世界和 NPC JSON 数据，转为 Schema 对象 |
| `persistence.py` | **存档系统**。`save()` / `load()` 函数，序列化状态到 JSON |
| `logger.py` | **TickLogger**。记录每轮 Tick 的输入输出到 `logs/` 目录 |
| `validation.py` | **StateValidator**。写入前校验（NPC 存在性、关系变化合法性等） |
| `tick_result.py` | **TickResult**。Tick 执行结果的数据类 |
| `providers/` | LLM Provider 实现目录（目前仅 DeepSeekClient，兼容 OpenAI API 格式） |

### 4.3 nodes/ — LLM 节点层（6 个节点 + 基类）

| 文件 | 职责 |
|------|------|
| `base.py` | **BaseNode** 抽象基类。定义 execute() 流程：收集数据→构造 Prompt→调 LLM→解析 JSON→转 Schema |
| `event_node.py` | N7 事件节点。判断玩家输入意图 |
| `perception_node.py` | N11 感知节点。NPC 信息闸门 |
| `reasoning_node.py` | N15 推理节点。NPC 推理 pending 事件 |
| `response_node.py` | N16 回应节点。NPC 生成回应 |
| `director_node.py` | N17 导演节点。整合叙事 |
| `propagation_node.py` | N18 传播节点。信息传播策略 |

### 4.4 Schema/ — 数据定义层（11 个 Schema 文件）

| 文件 | 定义内容 |
|------|----------|
| `world_schema.py` | WorldState、WorldDefinition、WorldRule、GlobalEvent 等 |
| `npc_schema.py` | NPC、NPCIdentity、PersonalityData、CurrentStateData、Emotion 等 |
| `event_schema.py` | Event、CurrentEvent、EventScope、EventType |
| `perception_schema.py` | PerceptionResult、NPCPerception |
| `memory_schema.py` | MemoryEntry、KnowledgeEntry、ObservationEntry |
| `belief_schema.py` | BeliefEntry、PendingEntry、ReasoningResult |
| `relationship_schema.py` | RelationshipValue、FavorabilityChange |
| `dialogue_schema.py` | ResponseResult、DialogueHistory |
| `director_schema.py` | DirectorResult、SceneMemory、DirectorStyleConfig |
| `action_schema.py` | GoalEntry、Item、NPCUpdateRecord |
| `location_schema.py` | Location |
| `schema_mapping.md` | 节点读写权限映射文档 |

### 4.5 config/ — 配置层（3 个 YAML）

| 文件 | 内容 |
|------|------|
| `runtime.yaml` | LLM 模式（mock/real）、引擎参数、日志级别 |
| `llm.yaml` | Provider 选择（deepseek/openai）、模型参数、各节点温度覆盖 |
| `world.yaml` | 世界名称、传播参数（max_hops/base_distortion）、NPC 容量限制 |

### 4.6 数据与资源

| 目录/文件 | 内容 |
|-----------|------|
| `prompts/` | 6 个 `.md` 文件，每个对应一个 LLM 节点的完整提示词模板 |
| `data/worlds/` | 世界定义 JSON（规则、隐藏事件、已知事件） |
| `data/npcs/` | NPC 定义 JSON（身份、性格、初始知识/信念/记忆/目标/关系/物品） |
| `saves/` | 运行时存档 JSON |
| `logs/` | Tick 日志 JSON（含各节点输入输出） |

### 4.7 tests/ — 测试（4 个文件）

| 文件 | 测试内容 |
|------|----------|
| `test_integration.py` | 端到端集成测试（完整 Tick 流程） |

## 五、关键设计约束

1. **读/写分离**：Node 只能读 WorldContext，不能直接修改 Entity。所有写入必须通过 UpdateEngine
2. **Node 不直接持有 LLMClient**：必须通过 LLMManager.chat() 调用
3. **暂态 vs 持久**：Node 输出是暂态结果，UpdateEngine 负责将其持久化
4. **Mock 优先测试**：通过 MockLLMManager.register_response() 预注册响应来模拟 LLM 行为
5. **Prompt 模板化**：`prompts/*.md` 含 Role/Goal/Input/Reasoning/Rules/Edge Cases/Output 七个标准部分

## 六、NPC 数据模型（10 张维护表）

| 表 | 对应字段 | 说明 |
|----|----------|------|
| form1 | memory / knowledge | 记忆和知识 |
| form2 | belief | 信念 |
| form3 | personality | 性格（大五人格 + traits） |
| form4 | goal | 生活目标 |
| form5 | relationship | 好感度/信任度 |
| form6 | current_state | 位置/情绪/动作/生命值 |
| form7 | observation | 观察记录 |
| form8 | inventory | 持有物品 |
| form9 | pending_reason | 待解释事件（触发推理的前置条件） |
| form10 | update_cost | 更新成本（暂未启用） |

## 七、运行方式

```bash
python main.py                     # 交互模式（Mock）
python main.py --world cangyue     # 真实 LLM 模式
python main.py --once "你好！"     # 单次执行
python main.py --mock --debug      # Mock + Debug 模式
python diagnose.py                 # 诊断数据流
pytest tests/ -v                   # 运行全部测试
```

LLM 模式通过 `config/runtime.yaml` 的 `llm_mode` 字段切换（`mock` / `real`）。真实模式需设置 `DEEPSEEK_API_KEY` 或 `OPENAI_API_KEY` 环境变量。
